## domonic issues found while comparing eventual.technology

- `ComputedStyleDeclaration` / CSSOM media rule matching caches `_cssom_rule_index` on the document without automatically invalidating it when `window.innerWidth` / `innerHeight` changes. Browser embedders must currently call their viewport setter and manually clear `document._cssom_rule_index` before resolving styles after a resize, otherwise `@media` rules can be evaluated against a stale viewport.
- `CSSMediaRule` traversal in domonic appears to prefer `conditionText` (a plain string) over the parsed `media` object. Because the style walker only checks a `.matches` attribute and strings do not have one, media blocks can be treated as matching unconditionally. This shows up on Bootstrap breakpoints while comparing `eventual.technology`, and is now pinned locally by `tests/layout/known_issues/media_queries.html`: at 500px/800px/1000px Chromonic receives the same `max-width: 960px` computed value instead of Chrome's breakpoint-specific value.

## 2026-09-14: real web-platform-tests (`tests/wpt/`, gitignored local checkout) run through the Chrome-vs-chromonic geometry harness

A local `tests/wpt/` checkout (the actual upstream web-platform-tests repo, not copied into chromonic's own test suite) is now used as a source of real, already-written CSS2.1/WPT test markup. The workflow: take a real test file from `tests/wpt/css/...` unmodified, auto-tag its elements with ids in a throwaway temp copy (never written back to the checkout or committed anywhere), run it through `tests/layout/harness`'s Chrome-vs-chromonic geometry+visual diff, and fix whatever chromonic gets wrong. First pass covered `wpt/css/CSS2/box-display/`, the simple (non "block-in-inline") files.

### Fixed this session (chromonic's own layer, not domonic)

- **`position:static` incorrectly honored authored `top`/`right`/`bottom`/`left`.** `style_bridge._position()` maps both `relative` and `static` onto Taffy's single "relative" position variant (Taffy has no separate "static"), but was still forwarding the authored `inset` for a static box. Taffy's "relative" applies `inset` as a real post-layout offset, so a `position:static` element with a stray `top`/`left` (or a UA default carrying one) shifted for no CSS-valid reason. Fixed in `style_bridge.to_dict()`: `inset` is forced to all-`auto` whenever the computed position is `static`.
- **`display:inline` honored authored `width`/`height`.** CSS 2.1 10.3.1 says these never apply to a non-replaced inline box; `style_bridge._display()` already collapses `inline` onto Taffy's plain `block` display (Taffy has no real inline mode), so an authored size became a hard box instead of being ignored. Fixed in `tree.build()`: `width`/`height` are forced to `auto` for a non-replaced, non-control tag with a trusted computed `display:inline` (see below for what "trusted" means).
- **`display:inline`/`inline-block` on an ordinary tag (`<div>`, `<p>`, ...) was never recognized as inline-level at all**, so e.g. `div div { display: inline-block }` (a real, simple `wpt/css/CSS2/box-display/display-005.xht` case) still stacked as an ordinary block instead of flowing inline. `_is_inline_level`'s old tag-name allowlist (`_USUALLY_INLINE_TAGS`: span/a/b/i/...) was a deliberate workaround for domonic reporting the *same* raw "inline" initial value for every tag alike with no UA stylesheet to disambiguate it -- but chromonic's own `ua_style.py` (added later, phase 11) already gives ordinary block tags a UA-default `display:block`, so that workaround was stale for any page going through `browser.load()`. Replaced with `_trusts_computed_inline()`: trust a computed inline/inline-block directly whenever the tag has an unambiguous UA default (`ua_style.BLOCK_DEFAULT_TAGS`) *and* the UA stylesheet actually ran, falling back to the old tag allowlist only for tags with no UA default at all (`<tr>`/`<td>`/`<th>`/...) or a raw DOM tree built without `browser.load()` (some unit tests skip it deliberately).
- **An inline formatting context's default cross-axis alignment was top, not the text baseline** (`_group_inline_element_runs`'s anonymous flex-row wrapper never set `align_items`), so a shorter inline-block sibling top-aligned with a taller one instead of sitting on the shared baseline. Fixed by setting `align_items: baseline` on that wrapper, matching what the separate text-mixed-content path already did.
- **The layout harness's own `chrome_runner.py` couldn't run any `.xht`/XHTML fixture at all** -- it injects an unclosed `<base href="...">` tag, which is fine under HTML parsing (void element) but breaks a strict-XML/XHTML document's well-formedness, silently truncating the parsed page and making Chrome emit no result. This blocked every real WPT `.xht` file (most of CSS2.1's own suite) until fixed by self-closing the injected tag (`<base href="..." />`).

### Confirmed but not fixed this session -- real, common gap in chromonic's own table layout

`display: table` / `table-row` / `table-cell` / `table-header-group` / `table-column` / `table-caption` etc. **only work when authored on the literal `<table>`/`<tr>`/`<td>`/`<th>` tags.** Chromonic's whole table projection is tag-name-gated in `tree.build()` (`if tag_name == "table"`, `if tag_name == "tr"`, `elif tag_name in ("td", "th")`); `style_bridge._display()` collapses every other CSS `display` value (including all the table-* values) onto plain `block`. A `<div style="display:table-row">` -- a completely ordinary, spec-legal CSS pattern -- gets no table behavior at all and just stacks as a block. This showed up in roughly a third of the simple `box-display/` files sampled (`display-006/007/009/011/013/014/015`, `containing-block-002`, ...), all otherwise-passing once the fixes above landed. Next real roadmap item: generalize the table special-casing to trigger off computed `display` (already resolved by `_describe`/`style_obj`) instead of `tagName`.

### Not chromonic's bug -- confirmed pre-existing, unrelated to this session's changes

`tests/test_chromonic.py::test_browser_load_applies_legacy_presentational_attributes`, `::test_load_image_decodes_an_svg_data_uri`, and `::test_layout_shares_ancestor_styles_only_within_one_pass` were already failing on `HEAD` before any of today's edits (verified via `git stash`); left alone.

## 2026-09-14 (cont'd): `wpt/css/CSS2/margin-padding-clear/` sweep (132 simple files sampled: `margin-*`, `padding-*`, `*-applies-to-*`, `*-em/percentage-inherit`, `margin-collapse-0*`, `margin-auto-on-block-box`)

### Fixed

- **Body's auto-height double-counted a margin that should have collapsed straight through a trailing empty child.** `_adjust_body_collapsed_margins()` computed body's Chrome-matching rect as the min/max `y`/`y+height` over all in-flow children -- but a CSS-empty child (zero height, zero border, zero padding; here an absolutely-positioned-only wrapper `<div>` with no in-flow content of its own) doesn't stop a preceding sibling's bottom margin from collapsing through it. That child's own Taffy `y` already sits *after* the escaped margin, so including its box in the min/max double-counted that same margin as if it were real content extent inside body. This one fix alone accounted for most of the recovered tests: the whole `margin-001..009`/`padding-001..004`-style family shares one `<div id="wrapper"><div id="reference"/><div id="div1">...</div></div>` template where `wrapper` is exactly this shape. Fixed by excluding CSS-empty children from the min/max unless *every* in-flow child is empty (then falling back to the original, unfiltered set so the correction never regresses to doing nothing).
- **Negative `padding` was applied literally instead of being an invalid, ignored declaration.** CSS 2.1 8.4 makes a negative padding value invalid outright (the whole declaration drops, leaving padding at its initial `0`); domonic's parser doesn't reject it. Fixed defensively in `style_bridge.to_dict()` by clamping every resolved padding edge to `>= 0` -- landing on the same outcome as "the declaration was dropped" without needing a real invalid-value signal, since padding's initial value already is zero.
- **`margin-top`/`margin-bottom` on a non-replaced inline box inflated its line's height.** CSS 2.1 10.3.1/10.6.1: these are accepted but have zero effect on a non-replaced inline box's height (only `margin-left`/`margin-right` add real spacing) -- Taffy doesn't know this on its own, and left as ordinary flex-item margins on the anonymous inline-run wrapper, they inflated the run's cross-axis size instead. Fixed alongside the existing `display:inline` width/height-forcing in `tree.build()`: the same `_trusts_computed_inline()`-gated branch now also zeroes `margin[0]`/`margin[2]`.

### Confirmed but not fixed -- larger, already-known gaps this family just kept re-surfacing

- **`display: table-row-group`/`table-row`/`table-cell` etc. authored on a `<div>`** -- the same tag-name-gated table limitation logged above, hit by most of the `margin-applies-to-00[1,4-7]`/`padding-applies-to-*` files (`display: table-row; margin: 50px` and friends).
- **`float` is still not a real exclusion-based layout model** -- `margin-right-004/005/006/007`, `margin-collapse-clear-*` (not sampled this round, same root cause) all use `float: left`/`right` and get ordinary in-flow block stacking instead.
- **An absolutely-positioned box with every inset (`top`/`right`/`bottom`/`left`) `auto` doesn't fall back to its static-flow position.** Per CSS 2.1 10.3.7/10.6.4, such a box should render where it would have landed in normal flow; chromonic instead places it at `(0, 0)` of its containing block. Seen in `margin-applies-to-009.xht`: an absolutely-positioned `<div id="wrapper">` with no inset properties at all landed at `x:0` instead of `x:8` (body's own UA margin, where it would have sat in flow). ### Confirmed, not yet fixed -- `overflow` (and other block-formatting-context triggers) are never passed to Taffy at all

`grep -rn overflow src/lib.rs python/chromonic/{tree,style_bridge}.py` finds nothing -- `overflow` isn't threaded through to the native layout tree in any form. CSS 2.1 8.3.1's real rule is that an element establishing a *new block formatting context* (`overflow` other than `visible`, `position: absolute`/`fixed`, `float`, or several `display` values) does not collapse its own margin with an in-flow child's -- e.g. `#parent { overflow: hidden }` containing a child with `margin-top: 2em` should keep that margin *inside* `#parent`'s box, not let it escape/collapse through `#parent`'s own top edge the way it would for an ordinary block. Taffy is a real CSS block-layout engine and near-certainly implements this correctly already *given the right input* -- the gap is that chromonic simply never tells it a box has non-`visible` overflow. Confirmed directly on `margin-collapse-009.xht`/`010`/`011` (`overflow: hidden` parent, `margin-top: 2em` child: Chrome keeps the child 40px lower, inside the parent; chromonic's child escapes 40px upward, colliding with the parent's own top edge) and `margin-collapse-013.xht` (`position: absolute` parent, same shape). This plausibly explains most of the remaining `margin-collapse-0[12,3]*` failures (`012`, `013`, `015a`, `020`, `032`, `037-041`), not just the three confirmed above.

Not attempted this session: fixing it for real needs a new `overflow` field threaded from `style_bridge.to_dict()` through the Rust FFI style dict (`src/lib.rs`) into Taffy's own `Style.overflow`, which needs a `cargo`/`maturin develop` rebuild of the native extension -- larger and riskier than a pure-Python change, and a good, well-scoped task to start a session with rather than land at the end of one.

## domonic issue: invalid property values are not rejected during parsing/cascade

CSS 2.1 (and every later spec) requires a syntactically-invalid property value to be dropped entirely, as if that one declaration were never written, leaving whatever the property's value was before it (the cascade's next-highest-priority declaration, or the initial value). domonic instead appears to accept the value as-is and let it participate in the cascade normally. Two concrete symptoms found this session:
- `padding-left: -1px` (negative padding is invalid, CSS 2.1 8.4) was applied literally rather than dropped -- chromonic now works around this defensively by clamping resolved padding to `>= 0` in `style_bridge.py`, which happens to produce the right *numeric* outcome only because padding's initial value is also `0`.
- `padding: 8px; padding: -8px;` (same property, second declaration invalid) -- chromonic's clamp above still lands on `0` here, not the correct `8px`, because by the time chromonic sees the cascade's result the earlier valid `8px` is already gone; only rejecting `-8px` *before* it enters the cascade (domonic's job) gets the right value in every case, not just the "one declaration, clamp is equivalent to reject" case.

## domonic issue: `<style>` content wrapped in `<![CDATA[ ... ]]>` is not parsed as CSS

Several real WPT `.xht` fixtures wrap their `<style>` element's content in a CDATA section (`<style type="text/css"><![CDATA[ ... ]]></style>`) -- valid, common XHTML practice, needed for strict XML well-formedness when the CSS contains characters like bare `&`. domonic's CSS parser doesn't strip the `<![CDATA[`/`]]>` markers before parsing, so the entire stylesheet inside such a `<style>` tag silently fails to apply -- every element keeps its un-cascaded initial/UA-default style instead. Confirmed directly on `wpt/css/CSS2/margin-padding-clear/margin-collapse-015a.xht`: `#inline-block`'s computed `display` stayed `block` (not the authored `inline-block`) and `div`'s computed `width` stayed `auto` (not the authored `5em`), despite an unambiguous, syntactically ordinary stylesheet. Not fixed this session -- either domonic's own `<style>`-content extraction should strip CDATA markers before handing the text to its CSS parser, or chromonic could work around it defensively the same way (strip `<![CDATA[`/`]]>` from a `<style>` tag's `textContent` before domonic ever sees it). Blocks verifying any CDATA-wrapped WPT fixture through the harness until fixed either way.

## 2026-09-14 (cont'd again): real-world site test (`untatme.com`, via `tools/chrome_probe.js`'s Chrome-side dump) -- three deep, high-leverage bugs found and fixed

Switched from the `tests/wpt/` fixture sweep to a real production site (a Tailwind v4 / Next.js page) after a Chrome-side probe dump (`tools/chrome_probe.js`, pasted into DevTools -> a downloadable JSON of every visible element's computed style + geometry) showed chromonic's own render of the same URL as badly broken: overlapping text, an unusably-sized search input, most of the page's content missing/collapsed. Rendered via `tests/layout/harness/native_runner.run(..., load_url=...)` (no `data-layout` tags needed for a screenshot) and cross-referenced every element in the probe JSON against chromonic's own `document.querySelector(same_selector).getBoundingClientRect()` to find the biggest divergences across the whole page in one pass, rather than guessing element-by-element. All three fixes below are real, and none were previously logged anywhere in this file.

### Fixed -- chromonic's own layer

- **`position: sticky` was mapped onto Taffy's `absolute`, pulling every sticky element out of the normal flow entirely.** `style_bridge._position()` grouped `sticky` with `absolute`/`fixed` (`"absolute" if kw.value in ("absolute", "fixed", "sticky") else "relative"`) -- since chromonic never simulates a scrolled state at all (always renders the initial, un-stuck position), the correct approximation is the *opposite* grouping: `sticky` behaves exactly like an ordinary in-flow element (Taffy's `relative`), with its `top`/`left`/etc. insets ignored the same way `to_dict()` already ignores them for `static` (a sticky element's inset never applies until actually stuck -- which chromonic never renders). This single bug collapsed the real site's entire `<header class="sticky top-0">` (and everything inside it) to a shrink-wrapped ~200x1.5px box positioned at the containing block's origin, which by itself accounted for most of the page's visible corruption -- a sticky header/nav is an extremely common real-world pattern this project's own synthetic fixtures apparently never happened to cover. Fixed in `style_bridge.py`: `_position()` now only groups `absolute`/`fixed`, and the existing `inset`-forced-to-auto branch in `to_dict()` now also covers `sticky`.

### Fixed -- domonic issues, patched locally via new `chromonic/domonic_*_patch.py` modules (same `install()`/`uninstall()`/`is_installed()` shape as the existing `domonic_canvas_patch.py`, auto-installed on `import chromonic.browser` so every entry point picks them up)

- **CSS Logical Properties (`padding-inline`, `margin-block-start`, `inset-inline-end`, ...) were silently dropped from the cascade entirely.** domonic's declaration tokenizer (`domonic.style._parse_css_declarations`) has no concept of logical properties -- a rule setting only `padding-inline`/`padding-block` (Tailwind v4's generated CSS uses exactly these, pervasively -- they alone accounted for the bulk of the real site's spacing) never produces `padding-left`/`padding-right`/etc. tuples, so those physical longhands stay at their initial `0`/`auto` regardless, while an unrelated, lower-priority reset rule (`* { padding: 0 }`, Tailwind's own preflight) wins by simply being the only one either sees. An input's `padding-top`/`-bottom` (`8px` in real Chrome) measured `0px`, collapsing its height from `44px` to `15px` and making it effectively unusable to click into -- matching the user's own report verbatim ("cant click in input box"). Patched in `python/chromonic/domonic_logical_properties_patch.py`: `_parse_css_declarations` now expands a logical property into its physical longhand(s) *at the tokenizer level* (same `!important` priority, same rule, same cascade position as the original) -- the one point where the expansion can ride on domonic's own already-correct specificity/layer/source-order competition instead of guessing at priority after the fact via a naive post-hoc `dict.setdefault` (tried first; it lost to the reset rule whenever that rule happened to be visited earlier, which is exactly the failure mode a real cascade must never have). LTR/horizontal-`writing-mode` only (`inline-start`/`-end` -> `left`/`right`, `block-start`/`-end` -> `top`/`bottom`), matching this project's already-documented lack of RTL/bidi support.
- **A `calc()` expression referencing a custom property (`calc(var(--spacing)*16)`, Tailwind v4's spacing scale -- used for essentially every length value on the real site, ~117 occurrences in one page's stylesheet) was never evaluated in `domonic.layout.LayoutStyle._from_computed()`, even though the *same* `calc()` resolves correctly through `getComputedStyle`.** `LayoutStyle._from_computed()` deliberately reads each property's raw, pre-used-value cascaded string (`computed._resolved.get`, not `getComputedStyle`'s own resolved accessors) so genuinely layout-dependent values (`auto`, a percentage) stay as typed placeholders for Taffy to resolve -- a legitimate design choice. But `_parse_length_or_percent()` already *tries* to evaluate any `calc()` it finds there (`_eval_calc_to_px`) without first expanding `var()` references the way `getComputedStyle`'s own resolution path does (`_expand_var_references`) -- so `calc(var(--spacing)*16)` still contains the literal, non-numeric `var(--spacing)` token, the evaluator silently gives up, and the result falls back to an opaque `Keyword` that `style_bridge._len()` can't turn into a number either, landing on `"auto"`. A `<div class="h-16">` (`height: calc(var(--spacing)*16)`, confirmed `64px` via `getComputedStyle`) produced a `LayoutStyle.height` of `Keyword(value='calc(var(--spacing)*16)')` -- silently `auto` instead of `64px` -- collapsing the real site's header content, and very likely nearly every other sized element on the page, toward zero/content height. Patched in `python/chromonic/domonic_layout_calc_var_patch.py`: `domonic.layout._parse_length_or_percent` now expands `var()` references (via the same `_expand_var_references`/`computed._custom_property` domonic already uses elsewhere) before evaluating a `calc()`, whenever one is present -- zero behaviour change for the overwhelming majority of values that don't reference a custom property.

Both patch modules found their target function via `sys.modules["domonic.style"]`/`sys.modules["domonic.layout"]` rather than `import domonic.style as _style` -- `domonic/__init__.py` overwrites its own `style` attribute with an (unrelated) `Style` class, so ordinary attribute-based access (including `import domonic.x as _x`, which resolves through package attribute access) silently returns the wrong object; only a `sys.modules` lookup by the full dotted name reaches the real submodule. Worth remembering for any future domonic patch in this project.
